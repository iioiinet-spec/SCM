11

재귀 함수 기초

함수가 자기 자신을 부를 수 있다. 반복문으로는 쓰기 어려운 문제가 세 줄로 풀리기도 하고, 반대로 아무 생각 없이 쓰면 호출 횟수가 폭발한다. 이 장의 마지막 실험이 PART 3에서 DP를 배워야 하는 이유를 숫자로 보여 준다.

학습 목표

  • 재귀 함수의 두 부분(종료 조건, 자기 호출)을 구분해 쓸 수 있다
  • 호출 스택이 쌓였다가 풀리는 모양을 추적 출력으로 확인할 수 있다
  • 간단한 재귀를 반복으로, 반복을 재귀로 바꿀 수 있다
  • 하노이 탑을 재귀로 풀고 이동 횟수가 2n−1임을 확인할 수 있다
  • 재귀 피보나치의 호출 횟수를 세어 왜 쓰면 안 되는지 설명할 수 있다
  • 재귀 깊이에 한계가 있다는 것을 알고 대략의 크기를 안다

01 — 도입 문제

자기 자신으로 정의하기

팩토리얼의 정의를 다시 읽어 보자.

수학적 정의
0! = 1
n! = n × (n−1)!
6장에서 쓴 코드
long long f = 1;
for (int i = 1; i <= n; i++) {
    f *= i;
}

정의는 자기 자신을 이용해 되어 있는데, 코드는 1부터 차례로 곱하는 전혀 다른 모양이다. 정의를 그대로 옮길 수는 없을까.

두 줄이다. 그리고 수학 정의와 한 줄씩 정확히 대응한다. 문제의 정의가 재귀적이면 코드도 재귀로 쓰는 것이 가장 짧고 정확하다.

그런데 재귀는 공짜가 아니다. 이 장의 마지막에서 같은 방식으로 피보나치를 쓰면 fib(45) 한 번에 36억 번의 호출이 일어나 11초가 걸린다. 같은 답을 반복문으로는 45번 만에 구할 수 있는데도.

이 장이 답할 질문 ① 재귀 함수가 반드시 끝나려면 무엇이 필요한가?
② 호출이 겹겹이 쌓일 때 메모리에서는 무슨 일이 일어나는가?
③ 재귀를 써야 할 때와 쓰면 안 될 때를 어떻게 구분하는가?
02 — 개념 정리

개념 정리

11.1재귀의 두 부분

모든 재귀 함수는 반드시 두 부분을 가진다. 하나라도 빠지면 끝나지 않는다.

부분하는 일팩토리얼에서
종료 조건
base case		더 이상 자기를 부르지 않고 답을 바로 돌려준다if (n == 0) return 1;
재귀 호출
recursive case		더 작은 문제로 자기를 부른다return n * fact(n-1);

6장에서 배운 반복문의 세 가지 점검(초기화·조건·갱신)과 짝이 맞는다. 종료 조건은 반복문의 조건이고, "더 작은 문제로 부르는 것"은 갱신이다. 매번 작아지지 않으면 영원히 끝나지 않는 것도 같다.

종료 조건은 반드시 도달 가능해야 한다 fact(-1)을 부르면 n이 −2, −3, …으로 가면서 n == 0에 영원히 닿지 않는다. 조건을 if (n <= 0)으로 바꾸거나, 애초에 음수가 들어오지 않도록 막아야 한다(5장의 거르기 먼저).

11.2호출 스택 — 쌓였다가 풀린다

함수를 부르면 돌아올 자리와 지역 변수를 스택에 쌓는다. 재귀는 돌아오기 전에 또 부르므로 계속 쌓이기만 하다가, 종료 조건에 닿는 순간부터 거꾸로 풀린다.

fact(4) 의 쌓임
fact(4)  → 4 * fact(3)
  fact(3)  → 3 * fact(2)
    fact(2)  → 2 * fact(1)
      fact(1)  → 1 * fact(0)
        fact(0)  → 1      ← 종료
풀림 — 거꾸로 계산된다
        fact(0) = 1
      fact(1) = 1 * 1  = 1
    fact(2) = 2 * 1  = 2
  fact(3) = 3 * 2  = 6
fact(4) = 4 * 6  = 24

중요한 것은 곱셈이 돌아오면서 일어난다는 점이다. 가장 깊이 들어간 호출이 가장 먼저 답을 내고, 그 답이 한 단계씩 위로 전달된다.

8장에서 큰 지역 배열이 왜 죽는지 배웠다. 같은 스택이다. 재귀가 깊어지면 호출 하나하나가 스택을 조금씩 먹는다.

11.3추적하는 법

재귀를 처음 배울 때는 머릿속으로 따라가기 어렵다. 들여쓰기 출력으로 직접 보는 것이 가장 빠르다.

들어올 때 한 번, 나갈 때 한 번 찍으면 쌓임과 풀림이 눈에 보인다. 재귀 문제가 안 풀릴 때 가장 먼저 할 일이 이 추적 출력이다.

11.4재귀와 반복은 서로 바꿀 수 있다

원리상 모든 재귀는 반복으로, 모든 반복은 재귀로 바꿀 수 있다. 어느 쪽이 쉬운지는 문제에 따라 다르다.

문제반복재귀권장
팩토리얼쉽다쉽다반복(스택 안 씀)
1~N 합쉽다가능반복
자릿수 합쉽다쉽다둘 다
하노이 탑매우 어렵다쉽다재귀
트리 순회어렵다쉽다재귀(PART 3)
피보나치쉽고 빠르다쓰면 안 된다반복

기준은 단순하다. 문제가 "자기와 같은 모양의 더 작은 문제 여러 개"로 쪼개지면 재귀, 그냥 차례로 처리하면 되면 반복이다.

11.5하노이 탑 — 재귀가 이기는 문제

기둥 세 개와 크기가 다른 원반 n개가 있다. 원반을 모두 1번에서 3번으로 옮기되, 한 번에 하나씩, 큰 원반을 작은 원반 위에 놓을 수 없다.

반복문으로 풀려고 하면 막막하다. 그런데 재귀로 생각하면 세 줄이다.

생각의 전부
n개를 1 → 3으로 옮기려면

① 위의 n−1개를 1 → 2로
② 가장 큰 1개를 1 → 3으로
③ n−1개를 2 → 3으로
왜 되는가
①과 ③은 "n−1개 옮기기"로
원래 문제와 같은 모양이다.
n이 0이 되면 할 일이 없다.
→ 종료 조건

①을 어떻게 하는지는 신경 쓰지 않는다. 그것도 같은 문제이므로 함수가 알아서 한다고 믿으면 된다. 이 "믿고 맡기는" 사고가 재귀의 핵심이며, PART 3의 분할 정복·백트래킹에서 그대로 쓰인다.

11.6피보나치의 함정

피보나치도 정의가 재귀적이다. 그대로 옮겨 보자.

정확히 동작한다. 문제는 속도다. 호출 횟수를 세어 보았다.

nfib(n)호출 횟수시간
10551770.000 초
206,76521,8910.000 초
30832,0402,692,5370.008 초
40102,334,155331,160,2810.981 초
451,134,903,1703,672,623,80510.843 초

n이 5 늘 때마다 호출이 약 11배가 된다. 같은 값을 수없이 다시 계산하기 때문이다. fib(5)를 계산하는 데 fib(3)이 두 번, fib(2)가 세 번 호출된다.

이미 구한 답을 적어 두면

한 번 구한 값을 배열에 저장해 두고 다시 묻지 않게 하면 어떨까.

핵심 두 줄
if (done[n]) { return memo[n]; }
done[n] = 1;
memo[n] = fib_memo(n-1) + fib_memo(n-2);
결과
fib(45)
  그냥 재귀 : 36억 7천만 호출
  저장하면  :       89 호출
  반복문    :       45 회
이것이 PART 3 DP의 출발점이다 "이미 구한 답을 적어 두고 다시 계산하지 않는다"는 이 발상을 메모이제이션이라고 하며, 동적 계획법(DP)의 절반이다. 36억을 89로 줄이는 것이 어떤 의미인지 여기서 체감해 두면, PART 3에서 DP를 배울 때 왜 그렇게까지 하는지 의문이 들지 않는다.

11.7재귀 깊이의 한계

호출마다 스택을 먹으므로 무한정 깊어질 수 없다. 실측해 보았다(스택 8 MB 환경).

함수의 지역 변수성공한 깊이죽은 깊이
거의 없음 (int 하나)200,000500,000
int buf[256] (1 KB)5,0008,000

함수 안에 지역 배열을 두면 깊이가 수십 분의 일로 줄어든다. 재귀 함수에는 지역 배열을 두지 않고, 필요한 배열은 전역으로 빼는 것이 원칙이다(8·9장과 같은 결론).

스택 초과는 메시지가 없다 그냥 Segmentation fault로 죽는다. 재귀를 쓴 코드가 큰 입력에서만 죽는다면 깊이를 먼저 의심한다. PART 3의 DFS에서 10만 개짜리 그래프를 다룰 때 실제로 부딪히는 문제다.

05 — 흔한 오류

흔한 오류 여섯 가지

오류 1종료 조건이 없다
long long fact(int n)
{
    return n * fact(n - 1);     // 멈추지 않는다
}

경고가 없다. 실행하면 스택이 가득 차 Segmentation fault로 죽는다. 무한 루프와 달리 프로그램이 멈추는 것이 아니라 죽는다는 점이 다르다.

고치는 법 — 재귀 함수를 쓸 때는 종료 조건을 맨 먼저 쓰고 나서 나머지를 채운다. 순서를 거꾸로 하면 빠뜨린다.
오류 2종료 조건에 도달하지 못한다
if (n == 0) { return 1; }
return n * fact(n - 1);
// fact(-1) 을 부르면 -2, -3, ... 영원히

종료 조건이 있는데도 끝나지 않는다. 호출이 종료 조건을 지나쳐 버리기 때문이다. 6장 연습 18번 (다)의 while (i != 10)과 완전히 같은 함정이다.

고치는 법 — == 대신 <=를 쓴다. if (n <= 0) { return 1; }. 그리고 호출 전에 입력을 검사한다.
오류 3더 작은 문제로 부르지 않았다
return n * fact(n);        // n이 그대로다
return n * fact(n + 1);    // 오히려 커진다

종료 조건도 있고 문법도 맞다. 그러나 문제가 작아지지 않으므로 종료 조건에 닿지 않는다. 오타 한 글자로 생기는 사고다.

고치는 법 — 재귀 호출의 인자가 반드시 종료 조건 쪽으로 움직이는지 눈으로 확인한다. 6장의 "갱신" 점검과 같다.
오류 4하노이의 기둥 역할을 틀렸다
hanoi(n-1, from, via, to);   // 올바름
hanoi(n-1, from, to, via);   // 틀림 — ①에서 to로 보내 버린다

경고도 없고 죽지도 않는다. 이동 횟수도 2n−1로 똑같이 나온다. 출력된 이동 순서만 틀린다. 채점에서만 발견된다.

고치는 법 — n = 2와 n = 3을 손으로 풀어 보고 출력과 대조한다. n = 3의 일곱 줄을 외워 두면 즉시 확인할 수 있다.
오류 5깊이를 생각하지 않고 재귀를 썼다
long long sum(int n) { if (n == 0) return 0; return n + sum(n-1); }
sum(1000000);      // 깊이 100만 → Segmentation fault

반복문으로는 100만 번이 0.003초인데(6장), 재귀로 쓰면 죽는다. 작은 입력에서는 멀쩡히 돌아가므로 제출 후에야 발견된다.

고치는 법 — 재귀를 쓰기 전에 최대 깊이를 계산한다. 수만 이상이면 반복으로 바꾼다. 특히 함수 안에 지역 배열을 두면 한계가 5천 수준까지 내려간다.
오류 6같은 값을 계속 다시 계산했다

피보나치가 대표다. 정확하지만 n = 45에서 11초가 걸린다. 채점 결과는 시간 초과다.

         (반복문이면 45회)

재귀 호출이 두 번 이상 나오고 인자가 겹칠 때 생긴다. 하노이처럼 두 번 불러도 겹치지 않으면 괜찮다.

고치는 법 — 호출 횟수를 전역 변수로 세어 본다. 답보다 훨씬 크면 메모이제이션을 쓰거나 반복으로 바꾼다.
이 장의 가장 중요한 교훈 재귀의 오류는 작은 입력에서 전부 통과한다. 깊이 초과(오류 5)도, 호출 폭발(오류 6)도 n이 10이면 아무 문제가 없다. 재귀를 쓸 때마다 두 가지를 계산한다. 최대 깊이는 얼마인가, 총 호출 횟수는 얼마인가.

정답과 해설

01
long long fact(int n) { if (n == 0) return 1; return n * fact(n-1); } — 반환형이 long long이어야 한다. 최대 깊이는 20으로 안전하다.
02
long long s(int n) { if (n == 0) return 0; return n + s(n-1); }
N = 100만이면 깊이 100만으로 스택을 초과해 Segmentation fault로 죽는다. 반복문으로는 0.003초인 작업이다(6장). 오류 5를 직접 겪게 하는 문제다.
03
long long power(int a, int b) { if (b == 0) return 1; return a * power(a, b-1); } — 깊이는 b. 240 = 1099511627776. 주의 — a * power(...)에서 a가 int이므로 (long long)a * power(...)로 쓰는 것이 안전하다(2장).
04
예제 3과 동일. 입력 0일 때 종료 조건에 바로 걸려 0이 나온다. 10장 반복 버전도 while (n > 0)이라 0을 출력하므로 결과가 같다.
05
int gcd(int a, int b) { if (b == 0) return a; return gcd(b, a % b); }
재귀 쪽이 짧다. 임시 변수 t가 필요 없기 때문이다. 깊이는 로그 수준이라 전혀 문제없다. 재귀를 쓰는 것이 더 나은 드문 예로 소개한다.
06
void down(int n) { if (n == 0) return; printf("%d ", n); down(n-1); } — 호출하기 전에 찍으므로 쌓이면서 출력된다.
07
void up(int n) { if (n == 0) return; up(n-1); printf("%d ", n); } — 호출을 먼저 하고 돌아오면서 찍는다.
지도 포인트 — 같은 구조에서 한 줄의 위치만 바꿨는데 출력 순서가 뒤집힌다. 11.2절의 "쌓임과 풀림"을 가장 선명하게 보여 주는 문제이므로 반드시 추적 출력과 함께 설명한다.
08
예제 2의 출력과 같다. 들여쓰기 깊이 = 스택에 쌓인 호출의 수. fact(4)면 최대 깊이 5(0까지)이고, 가장 깊은 곳에서 먼저 답이 나온다.
09
표준 코드와 동일. 검증: n = 3의 일곱 줄이 1 3 / 1 2 / 3 2 / 1 3 / 2 1 / 2 3 / 1 3과 일치하는지 확인시킨다.

printf("%lld\n", (1LL << n) - 1); — N = 60이면 260−1 = 1152921504606846975. 1 << n으로 쓰면 n ≥ 31에서 깨진다(4장). 재귀를 돌리면 1018번이라 영원히 끝나지 않는다는 점을 짚는다.

지도 포인트 — n이 5 늘 때마다 호출이 약 11배가 된다. 이 비율을 학생이 직접 계산하게 한다.

예제 5와 동일. fib(90) = 2880067194370816120, 호출은 179회 수준(n마다 두 번씩 들어오고 한 번만 계산).
주의 — 배열 크기를 91 이상으로 잡아야 memo[90]이 범위 안이다(8장 오류 1). fib(93)은 long long을 넘어 음수가 된다.
13
10장 표준 코드가 그대로 반복 버전이다. 지도 포인트 — 두 버전을 1부터 10,000까지 전부 돌려 결과를 비교하는 자동 대조 코드를 짜게 한다. 이것이 PART 2에서 배울 "기준 정답과 대조하기"의 첫 연습이다.
14
void bin(int n) { if (n == 0) return; bin(n / 2); printf("%d", n % 2); }
07번과 같은 구조다. 돌아오면서 찍어야 높은 자리부터 나온다. 호출하기 전에 찍으면 1011로 거꾸로 나온다. 13 → 1101.
15
int is_pal(int a[], int l, int r)
{
    if (l >= r) { return 1; }            // 종료 ①: 다 봤다
    if (a[l] != a[r]) { return 0; }      // 종료 ②: 다르다
    return is_pal(a, l + 1, r - 1);
}
종료 조건이 둘인 것이 이 문제의 핵심이다. 하나는 성공, 하나는 실패다. l >= r로 쓰면 길이가 짝수일 때(l > r)와 홀수일 때(l == r)가 모두 처리된다.
16
교재 집필 환경(스택 8 MB)의 실측값.
지역 변수성공실패
거의 없음깊이 200,000깊이 500,000
int buf[256] (1 KB)깊이 5,000깊이 8,000
약 40배 차이다. 학생마다 값이 다를 수 있으나 "지역 배열이 깊이를 크게 깎는다"는 경향은 반드시 같게 나온다.
지도 포인트 — PART 3의 DFS에서 10만 개 노드를 재귀로 따라갈 때 이 계산이 실제로 필요하다. 그때를 위해 지금 수치 감각을 만들어 둔다.
17
long long power(long long a, int b)
{
    if (b == 0) { return 1; }
    long long h = power(a, b / 2);
    if (b % 2 == 0) { return h * h; }
    return h * h * a;
}
핵심 — power(a, b/2)를 한 번만 부르고 변수에 담는다. power(a,b/2) * power(a,b/2)로 쓰면 두 번 계산해 효과가 사라진다(오류 6과 같은 함정).
호출 횟수 — 03번은 b번, 이 방법은 약 log₂b번. b = 109이면 10억 번 대 30번이다.
지도 포인트 — "절반으로 줄이기"가 로그 시간을 만든다는 첫 경험이다. PART 3 이분 탐색, PART 4 분할 정복으로 이어진다.
18
① fib(5)의 노드 수는 15개로 예제 4의 호출 횟수와 일치한다.
② fib(2)는 3번 나타난다. (fib(3)은 2번, fib(1)은 5번, fib(0)은 3번.)
③ 메모이제이션은 두 번째로 나타난 노드부터 그 아래 전체를 잘라 낸다. fib(3)의 두 번째 등장 아래가 통째로 사라지므로, 트리가 사실상 한 줄짜리 사슬이 된다.
지도 포인트 — 트리를 직접 그려 본 학생은 "왜 호출이 지수적으로 느는가"를 설명할 수 있게 된다. 말로 설명하지 말고 반드시 그리게 한다.
19
⑴ 반복 — 재귀면 깊이 106으로 죽는다. 호출 횟수 자체는 문제없지만 깊이가 치명적이다.
⑵ 재귀 — 깊이 20, 호출 약 221회. 둘 다 안전하고, 반복으로 쓰면 오히려 매우 어렵다.
⑶ 주의 필요 — 재귀가 자연스럽지만 최악의 경우 깊이가 105가 된다. 지역 변수를 최소로 하면 대개 통과하나, 여유가 없으면 스택을 직접 만들어 반복으로 바꾼다(PART 3에서 다룬다).
⑷ 반복 또는 메모이제이션 — 그냥 재귀면 fib(50)에서 약 400억 호출로 불가능하다.
지도 포인트 — 판단 기준이 깊이와 호출 횟수 두 가지라는 것을 표로 정리시킨다. ⑴은 깊이가, ⑷는 횟수가 문제다.
20
① 이동 횟수는 똑같이 2n−1이다. 재귀 구조가 같기 때문이다.
② 규칙을 위반한다. 기둥마다 원반을 쌓아 두는 배열을 만들어 검사하면, 큰 원반이 작은 원반 위에 올라가는 이동이 나온다.
③ 횟수는 재귀 호출의 구조만으로 정해지고, 기둥 이름을 어떻게 섞든 두 번의 n-1 호출과 한 번의 출력이라는 모양은 변하지 않는다. 따라서 횟수가 맞다고 답이 맞는 것이 아니다. 출력의 내용을 검증해야 한다.
검증 코드 예 — 기둥 3개를 스택처럼 쓰는 배열을 두고, 각 이동마다 "출발 기둥이 비어 있지 않은가", "옮길 원반이 도착 기둥의 맨 위보다 작은가"를 확인한다. 이것이 PART 2에서 배울 자체 채점 스크립트의 축소판이다.
08 — 마무리

이 장을 마치기 전 점검

  • 재귀 함수를 쓸 때 종료 조건을 맨 먼저 쓴다
  • 재귀 호출의 인자가 종료 조건 쪽으로 움직이는지 확인한다
  • 종료 조건을 == 대신 <=로 쓴다
  • 재귀를 쓰기 전에 최대 깊이를 계산한다
  • 재귀를 쓰기 전에 총 호출 횟수를 계산한다
  • 재귀 함수 안에 지역 배열을 두지 않는다
  • 안 풀리면 들여쓰기 추적 출력부터 찍는다
  • 같은 값을 다시 계산하고 있으면 메모 배열을 둔다
