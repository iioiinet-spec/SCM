02

변수와 자료형, 오버플로

변수 하나가 차지하는 비트 수가 표현할 수 있는 값의 범위를 정하고, 그 범위를 넘는 순간 계산은 조용히 틀린 답을 낸다. 올림피아드에서 가장 많이 나오는 "맞는 알고리즘, 틀린 답"의 1순위 원인이다.

학습 목표

  • char·short·int·long long·double의 크기와 표현 범위를 말할 수 있다
  • 비트 수에서 표현 범위가 어떻게 나오는지 계산할 수 있다
  • limits.h의 상수로 범위를 직접 출력해 확인할 수 있다
  • 1부터 N까지의 합이 int로 틀려지는 N을 실험으로 찾고 long long으로 고칠 수 있다
  • 중간 계산에서만 넘치는 오버플로를 알아보고 형변환 위치를 올바르게 잡을 수 있다

2차시limits.h · 표준 코드 · 단계 예제 1~5
3차시흔한 오류 6종 · 연습 문제 · 확인 평가
01 — 도입 문제

1부터 N까지 더하면 어디서 틀릴까

1부터 N까지의 합은 N(N+1)/2다. 초등학교에서도 배우는 식이고, C로 옮기는 데 한 줄이면 충분하다.

이 코드에 N을 점점 키워 넣어 보자. 아래는 실제 실행 결과다.

N위 코드의 출력참값판정
1000500500500500맞음
4634010737209701073720970맞음
46341-10737163371073767311틀림 — 음수가 됨
65536327682147516416틀림 — 그럴듯한 값

N = 46341에서 답이 음수로 뒤집힌다. 더 무서운 것은 N = 65536이다. 출력 32768은 음수도 아니고 0도 아니어서, 코드를 아무리 들여다봐도 틀렸다는 신호가 없다.

이 장이 답할 질문 ① 왜 하필 46341인가?
② 1부터 한 개씩 더해 나가면 틀리기 시작하는 N도 46341일까?
③ int를 long long으로 바꾸기만 하면 끝나는가?

②의 답을 미리 말하면 아니다. 한 개씩 더하는 방식은 N = 65536까지 버틴다. 같은 합을 구하는 두 방법이 서로 다른 지점에서 무너진다는 사실이 이 장의 핵심이다.

02 — 개념 정리

개념 정리

2.1비트 수가 범위를 정한다

변수는 메모리에 일정한 개수의 비트를 차지한다. 비트 하나는 0 또는 1이므로, n비트로는 서로 다른 2n가지 상태만 구별할 수 있다. 자료형의 범위는 여기서 곧바로 따라 나온다.

부호 있는 정수는 맨 앞 비트 하나를 부호에 쓰므로, n비트일 때 범위는 −2n−1 ~ 2n−1−1이다. 음수 쪽이 하나 더 많은 것은 0이 양수 쪽에 들어가기 때문이다.

비트가짓수부호 있는 범위해당 자료형
8256−128 ~ 127char
1665,536−32,768 ~ 32,767short
32약 43억−2,147,483,648 ~ 2,147,483,647int
64약 1844경약 ±9.22 × 1018long long

외울 숫자는 하나다. int의 상한은 약 21억. 문제의 제약 조건에서 계산 결과가 21억을 넘을 가능성이 보이면 그 순간 long long을 꺼낸다.

long은 쓰지 않는다 long의 크기는 환경마다 다르다. 리눅스·macOS에서는 8바이트지만 윈도우에서는 4바이트라 int와 똑같다. 집에서 되던 코드가 시험장에서 틀리는 전형적인 원인이다. 큰 정수가 필요하면 언제나 long long을 쓴다.

2.4오버플로: 범위를 넘으면 되감긴다

int의 최댓값에 1을 더하면 어떻게 될까. 오류가 나지도, 프로그램이 멈추지도 않는다.

CODE
int a = INT_MAX;
a = a + 1;
printf("%d\n", a);
OUTPUT
-2147483648

자동차 주행 거리계가 999999에서 000000으로 돌아가듯, 비트가 모자라면 값이 반대쪽 끝으로 되감긴다. 이것을 오버플로라고 한다. 도입 문제에서 답이 음수로 뒤집힌 이유가 바로 이것이다.

이제 ①번 질문에 답할 수 있다. 공식 N * (N + 1) / 2에서 컴퓨터는 곱셈을 먼저 한다. 그래서 최종 답이 아니라 중간값 N×(N+1)이 21억을 넘는 순간부터 틀린다. 46341 × 46342 ≈ 21.5억으로 여기서 처음 넘는다. 반면 한 개씩 더하는 방식은 중간값이 곧 부분합이므로, 합 자체가 21억을 넘는 65536에서야 무너진다.

기억할 원칙 오버플로는 최종 답이 아니라 계산 도중에 거쳐 가는 가장 큰 값을 기준으로 판단한다. 답이 작아도 중간에 큰 수가 생기면 넘친다.

2.5double과 char

double — 넓지만 정확하지 않다

double은 10308까지 담지만, 유효숫자는 약 15~16자리뿐이다. 그래서 큰 정수를 넣으면 뒷자리가 잘린다.

CODE
printf("%.20f\n", 0.1 + 0.2);
printf("%.1f\n", 9007199254740993.0);
OUTPUT
0.30000000000000004441
9007199254740992.0

0.1과 0.2는 2진 소수로 정확히 표현되지 않아 아주 작은 오차가 남는다. 따라서 실수끼리 ==로 비교하면 안 된다. 정수로 풀 수 있는 문제는 끝까지 정수로 푸는 것이 정답이다.

char — 1바이트짜리 작은 정수

C에서 char는 문자 전용 자료형이 아니라 −128 ~ 127을 담는 정수다. 문자는 아스키 코드라는 번호로 저장될 뿐이다.

CODE
char c = 'A';
printf("%d %c\n", c, c + 1);
printf("%d\n", 'z' - 'a');
char d = 127; d = d + 1;
printf("%d\n", d);
OUTPUT
65 B
25
-128

'z' - 'a'가 25인 것은 알파벳 번호가 연속이기 때문이다. 8장 이후의 문자 처리 문제에서 계속 쓰인다. 그리고 char도 127을 넘으면 똑같이 되감긴다.

05 — 흔한 오류

흔한 오류 여섯 가지

아래 메시지는 gcc 13.3.0에서 실제로 출력된 것이다. 이 장의 오류는 1장과 성격이 다르다. 대부분 컴파일에 성공하고, 조용히 틀린 답을 낸다.

오류 1결과를 int에 담았다

계산은 맞는데 받는 그릇이 작다. 컴파일러는 아무 말도 하지 않는다.

int sum = (long long)N * (N + 1) / 2;   // 8바이트 값을 4바이트에 담음

곱셈은 안전하게 수행됐지만, 그 결과를 int 변수에 넣는 순간 잘려 나간다.

고치는 법 — 넘칠 수 있는 값을 담는 변수는 처음부터 long long으로 선언한다.
오류 2형변환 위치가 늦다

예제 2의 세 번째 식이다. long long이라는 글자에 속지 않아야 한다.

long long bad  = (long long)(N * (N + 1) / 2);   // 이미 늦음
long long good = (long long)N * (N + 1) / 2;     // 올바름
고치는 법 — 괄호 안에서 가장 먼저 수행되는 연산의 피연산자에 형변환을 붙인다.
오류 3long long을 %d로 출력

printf("%d\n", v);에서 v가 long long인 경우다.

fmt.c:4:14: warning: format '%d' expects argument of type 'int',
            but argument 2 has type 'long long int' [-Wformat=]
    4 |     printf("%d\n", v);
      |             ~^     ~
      |              |     |
      |              int   long long int
      |             %lld

gcc가 고칠 서식까지 %lld로 알려 준다. 그래도 경고일 뿐이라 실행은 된다. v가 100억일 때 출력은 1410065408, 즉 아래쪽 32비트만 찍힌다.

고치는 법 — long long은 출력 %lld, 입력 %lld. 예외 없다.
오류 4scanf로 long long을 %d로 입력

출력보다 훨씬 위험하다.

fmt.c:6:13: warning: format '%d' expects argument of type 'int *',
            but argument 2 has type 'long long int *' [-Wformat=]

8바이트 변수에 4바이트만 채워 넣으므로 나머지 4바이트는 이전에 들어 있던 쓰레기값이 남는다. 그런데 작은 수를 넣어 시험해 보면 우연히 맞는 값이 나오기도 한다. 테스트에서 통과하고 채점에서 틀리는 최악의 경우다.

고치는 법 — "경고가 떴지만 결과는 맞던데요"는 통하지 않는다. 경고 0개를 지킨다.
오류 5long을 믿었다

long sum = ...;으로 써 놓고 8바이트라고 가정하는 경우다. 리눅스에서는 통과하고 윈도우에서는 int와 똑같이 21억에서 넘친다.

경고도 오류도 나지 않는다. 환경을 바꾸기 전까지는 발견할 방법이 없다.

고치는 법 — long을 아예 쓰지 않는다. 4바이트면 int, 8바이트면 long long 둘 중 하나만 쓴다.
오류 6큰 정수를 double로 처리

"double이 범위가 제일 넓으니까 안전하겠지"라는 오해다.

printf("%.1f\n", 9007199254740993.0);   →   9007199254740992.0

마지막 자리가 1에서 2로 바뀌었다. double은 범위는 넓지만 유효숫자가 약 15~16자리라서, 그보다 긴 정수는 가까운 값으로 반올림된다. 정수 문제에서 double을 쓰면 답이 1 차이로 틀린다.

고치는 법 — 정수 문제는 정수형으로 끝까지 간다. double은 실수 계산이 꼭 필요할 때만 쓴다.
이 장의 가장 중요한 교훈 1장의 오류는 컴파일이 안 되게 만들어 스스로 드러났다. 이 장의 오류는 컴파일도 되고 실행도 되며 작은 입력에서는 정답까지 낸다. 그래서 제출 전에 제약 조건의 최댓값을 직접 넣어 보는 것이 유일한 방어책이다.

int a = -1;
unsigned int b = 1;
printf("%s\n", (a < b) ? "a is smaller" : "b is smaller");

제약 조건에서 자료형 결정하기 — 어떤 문제의 조건이 다음과 같다. "N개의 정수가 주어진다(1 ≤ N ≤ 200,000, 각 정수의 절댓값은 1,000,000,000 이하). 모든 수의 합과, 가장 큰 두 수의 곱을 출력하라." ① 합을 담을 자료형 ② 곱을 담을 자료형을 각각 정하고, 최악의 경우 값을 직접 계산해 근거를 보여라.

07 — 확인 평가 해설

정답과 해설

※ 이 절은 교사용 통합본에만 수록한다. 학생 배부용에서는 제거한다.

01
printf("int %zu bytes\n", sizeof(int)); 형태로 여섯 줄. 지도 포인트 — long이 8바이트로 나오는 것을 보여 주고, 윈도우에서는 4바이트임을 반드시 덧붙인다.
02
#include <limits.h> 후 printf("%d %d\n", INT_MIN, INT_MAX);. 숫자를 직접 적은 답안은 오답 처리한다. 상수를 쓰는 습관이 목적이다.
03
long long sum = (long long)N * (N + 1) / 2; — N의 최댓값 106에서 중간값이 약 1012이므로 반드시 형변환이 필요하다. int로 제출한 답안은 N=1000000에서 바로 틀린다.
04
printf("%lld\n", (long long)A * B); — 1012는 int 범위 밖이다. 흔한 오답: long long p = A * B;(곱셈이 이미 int로 끝남).
05
2×106의 세제곱은 8×1018. LLONG_MAX는 약 9.22×1018이므로 간신히 들어간다. (long long)A * A * A로 쓴다. 지도 포인트 — 이 문제는 "long long도 무한하지 않다"를 느끼게 하는 자리다. A가 3,000,000이면 넘친다.
06
char c; scanf("%c", &c); printf("%d %d\n", c, c - 'a'); — 'k'는 107, 'a'는 97이므로 10.
07
printf("%c\n", c - 'a' + 'A'); 또는 c - 32. 전자를 권장한다. 후자는 32라는 숫자의 의미가 코드에 드러나지 않는다.
08
INT_MAX + 1 → −2147483648, INT_MIN - 1 → 2147483647. 양 끝이 서로 이어져 있다는 것을 관찰시킨다. 보충 — 부호 있는 정수의 오버플로는 C 표준상 정의되지 않은 동작이라, 최적화 옵션에 따라 다른 결과가 나올 수도 있음을 교사가 알고 있어야 한다.
09
105 × 105 = 1010 > 21억이므로 int로 부족하다. (long long)W * H. 근거를 주석으로 쓰게 하는 것이 이 문제의 목적이다.
10
세 수의 합은 최대 6×109으로 int 범위를 넘는다. long long s = (long long)a + b + c; 후 printf("%.2f\n", s / 3.0);. 흔한 오답: (a+b+c)/3.0 — 괄호 안이 이미 int로 넘친다.
11
long long total = (long long)n * (2LL * a + (long long)(n - 1) * d) / 2; — 안쪽 (n-1)*d도 106×103=109으로 아슬아슬하다. 지도 포인트 — 중첩된 식에서는 모든 중간값을 점검해야 한다. 바깥쪽만 형변환한 답안이 많이 나온다.
12
입력도 long long이므로 scanf("%lld", &s);. 이어서 s/86400, s/3600%24, s/60%60, s%60. 흔한 오답: scanf("%d", &s) — 오류 4와 같은 경고가 뜬다.
13
① 최대 10,000 → int(short도 가능하나 실무상 int) ② 최대 109 → int로 가능하지만 21억에 근접하므로 long long 권장 ③ 1012 → long long ④ 20! ≈ 2.43×1018 → long long(21!은 넘침). 지도 포인트 — ②처럼 "되기는 되지만 아슬아슬한" 경우의 판단 기준을 토론시킨다.
14
둘 다 9007199254740992.0으로 같게 출력된다. double의 유효숫자는 약 15~16자리인데 이 수는 16자리이고, 253을 넘어서는 홀수는 표현 자체가 불가능해 가까운 짝수로 반올림된다.
15
126 → 127 → −128 → −127 → −126. 127이 char의 최댓값이므로 1을 더하는 순간 최솟값으로 되감긴다. 1장에서 배운 printf 다섯 번으로 작성하게 한다.
16
A + B는 최대 4×109으로 int를 넘는다. 두 가지 해법을 모두 받는다.
⑴ printf("%lld\n", ((long long)A + B) / 2);
⑵ A + (B - A) / 2 — 차이는 범위를 넘지 않으므로 int만으로 안전하다.
지도 포인트 — ⑵는 이분 탐색의 중간 지점 계산에서 그대로 쓰인다(PART 3). 여기서 한 번 보여 두면 나중에 설명이 쉬워진다.
17
공식 버전은 N = 46341, 누적 버전은 N = 65536에서 처음 틀린다.
공식 버전의 중간값은 N × (N+1)이고, 46341 × 46342 ≈ 2.148×109으로 INT_MAX(약 2.147×109)를 처음 넘는다. 누적 버전의 중간값은 부분합 그 자체이므로, 합이 INT_MAX를 넘는 65536에서야 넘친다.
결론 — 오버플로 시점은 최종 답이 아니라 계산 경로에서 나타나는 최댓값이 정한다. 같은 답을 구하는 두 알고리즘의 안전 한계가 다를 수 있다.
18
int는 12!(479,001,600)까지 정확하고 13!에서 틀린다(6,227,020,800이 1,932,053,504로 나옴). long long은 20!(2,432,902,008,176,640,000)까지 정확하고 21!에서 음수가 된다.
근거: 13! ≈ 6.2×109 > 2.1×109, 21! ≈ 5.1×1019 > 9.2×1018.
19
출력은 b is smaller. int와 unsigned int를 비교하면 int 쪽이 unsigned로 변환되어 −1이 4,294,967,295가 되기 때문이다.
정리 문장 예시 — "unsigned는 음수를 표현하지 못할 뿐 아니라 섞여 쓰이면 비교 결과까지 뒤집으므로, 올림피아드 코드에서는 쓰지 않는다."
20
① 합 — 최악은 200,000 × 109 = 2×1014. int 범위를 다섯 자리 가까이 넘으므로 long long.
② 곱 — 최악은 109 × 109 = 1018. LLONG_MAX(약 9.22×1018) 안에 들어가므로 long long으로 충분하다. 단 곱하기 전에 형변환해야 한다.
지도 포인트 — 이 문제의 목적은 "N과 값의 범위를 곱해 최악의 경우를 손으로 계산하는 절차"를 몸에 붙이는 것이다. 앞으로 모든 문제에서 이 계산을 먼저 하게 한다.
08 — 마무리

이 장을 마치기 전 점검

  • int의 상한이 약 21억이라는 것을 외우고 있다
  • 제약 조건을 보고 최악의 경우 값을 손으로 계산할 수 있다
  • 최종 답이 아니라 중간값을 기준으로 오버플로를 판단한다
  • 형변환을 넘치기 전 위치에 붙일 수 있다
  • long long은 입력도 출력도 %lld로 쓴다
  • long과 unsigned는 쓰지 않는다
  • 정수 문제를 double로 풀지 않는다
다음 장 예고 — 03장 서식 입출력 이 장에서 %lld와 %zu가 갑자기 등장했다. 서식 지정자가 몇 종류나 있고 각각 언제 쓰는지, 그리고 1장에서 미뤄 둔 scanf의 반환값과 EOF 처리를 다음 장에서 정리한다.
