01 — 도입 문제

왜 컴파일부터 배우는가

정보올림피아드 1차 시험은 종이에 쓴 코드가 아니라 실제로 돌아가는 프로그램으로 평가한다. 아무리 알고리즘을 잘 떠올려도 컴파일이 되지 않으면 0점이다. 그래서 첫 수업의 목표는 알고리즘이 아니라, 머릿속 생각을 실행 파일까지 옮기는 통로를 뚫는 것이다.

다음 질문에 지금 답해 보자. 답을 모르는 채로 이 장을 시작해도 좋다.

생각해 볼 질문 ① 우리가 작성한 .c 파일을 컴퓨터는 그대로 실행할 수 있을까?
② return 0;의 0은 누구에게 돌려주는 값일까?
③ 화면에 글자를 쓰는 것과 파일에 글자를 쓰는 것은 프로그램 입장에서 얼마나 다를까?
④ 세미콜론 하나를 빠뜨리면 컴파일러는 몇 번째 줄을 지목할까?

④번은 특히 중요하다. 컴파일러가 알려 주는 줄 번호는 실수한 줄이 아니라 실수를 알아챈 줄인 경우가 많다. 이 차이를 모르면 멀쩡한 줄을 몇 분씩 노려보게 된다. 이 장의 마지막 절에서 실제 메시지로 확인한다.

02 — 개념 정리

개념 정리

2.1gcc가 하는 네 단계

소스 파일 add.c는 사람이 읽는 글자일 뿐이다. CPU가 실행하는 것은 기계어다. gcc는 그 사이를 네 단계로 잇는다.

단계하는 일결과물직접 보려면
전처리
preprocess		#include를 실제 내용으로 바꾸고 주석을 제거확장된 소스 .igcc -E add.c
컴파일
compile		C 문법을 검사하고 어셈블리로 번역어셈블리 .sgcc -S add.c
어셈블
assemble		어셈블리를 기계어로 변환목적 파일 .ogcc -c add.c
링크
link		printf 같은 라이브러리 함수를 연결실행 파일gcc -o add add.c

오류 메시지를 읽을 때 이 구분이 바로 쓸모가 있다. error:로 시작하고 줄 번호가 붙어 있으면 컴파일 단계의 문법 오류이고, /usr/bin/ld:나 undefined reference to가 보이면 링크 단계의 문제다. 둘은 고치는 방법이 다르다.

2.2수업에서 쓸 컴파일 명령

옵션의미
-std=c11C11 표준으로 해석한다. 이 교재의 모든 코드는 C11 기준이다.
-Wall경고를 폭넓게 켠다. 경고는 오류가 아니지만, 대부분의 실전 실수는 경고에서 먼저 드러난다.
-o add실행 파일 이름을 add로 지정한다. 생략하면 a.out이 된다.
./add현재 폴더의 add를 실행한다. 앞의 ./를 빼면 찾지 못한다.
최적화 옵션은 나중에 실전 채점 환경에서는 -O2를 함께 쓴다. 다만 -O2를 켜면 scanf의 반환값을 쓰지 않았다는 경고가 추가로 나온다. 그 경고의 의미와 처리 방법은 3장 서식 입출력에서 다루므로, 1장에서는 -O2 없이 연습한다.

2.3main의 반환값

main은 우리가 부르는 함수가 아니라 운영체제가 부르는 함수다. 그래서 main이 돌려주는 값은 프로그램을 실행시킨 쪽, 즉 운영체제나 채점 프로그램에게 간다. 이 값을 종료 코드라고 한다.

반환값뜻
return 0;정상 종료. 올림피아드 제출 코드는 반드시 0으로 끝나야 한다.
return 1; 등비정상 종료. 채점기는 이것을 런타임 오류로 처리한다.
종료 코드는 0~255만 전달된다 return 300;으로 끝낸 프로그램의 종료 코드를 확인하면 44가 나온다. 300을 256으로 나눈 나머지이기 때문이다. 종료 코드는 1바이트만 전달되므로, 계산 결과를 return으로 내보내려는 시도는 통하지 않는다. 답은 반드시 printf로 출력한다.

2.4표준 입력과 표준 출력

C 프로그램은 시작할 때 세 개의 통로를 자동으로 가진다. 이 세 통로를 묶어 표준 스트림이라고 한다.

스트림기본 연결 대상쓰는 함수용도
stdin
표준 입력		키보드scanf, getchar문제의 입력 데이터를 받는다
stdout
표준 출력		화면printf, putchar정답을 출력한다. 채점 대상은 이것뿐이다.
stderr
표준 오류		화면fprintf(stderr, ...)디버깅용 메시지. 채점에 포함되지 않는다

핵심은 통로가 어디에 연결되는지는 프로그램이 정하지 않는다는 점이다. 같은 프로그램이라도 실행할 때 연결을 바꿀 수 있다.

채점 프로그램이 하는 일도 정확히 이것이다. 우리 프로그램의 stdin에 입력 파일을 연결하고, stdout으로 나온 내용을 정답 파일과 글자 단위로 비교한다. 그래서 "숫자를 입력하세요" 같은 안내문을 printf로 찍으면 틀린다. 안내문이 필요하면 stderr로 보낸다.

2.5세미콜론과 블록

C는 줄바꿈을 문장의 끝으로 보지 않는다. 문장의 끝은 오직 세미콜론이다. 그래서 다음 두 코드는 컴파일러에게 완전히 같다.

A
int a, b;
scanf("%d %d", &a, &b);
printf("%d\n", a + b);
B — 같은 프로그램
int a,b;scanf("%d %d",&a,&b);printf(
"%d\n",a+b);

B처럼 써도 돌아가지만 쓰지 않는다. 줄바꿈과 들여쓰기는 컴퓨터가 아니라 세 시간 뒤의 자신을 위한 것이다. 시험장에서 자기 코드를 못 읽어 시간을 날리는 일이 실제로 일어난다.

중괄호 { }는 여러 문장을 하나의 덩어리로 묶는 블록을 만든다. main의 몸통도 블록이고, 뒤에서 배울 조건문·반복문·함수도 모두 블록을 쓴다. 여는 중괄호와 닫는 중괄호는 반드시 짝을 이루며, 짝이 맞지 않으면 컴파일러는 파일의 맨 끝에서 오류를 보고한다.

03 — 표준 코드

표준 코드: 두 수의 합

아래 코드는 이 교재에서 수백 번 변형될 뼈대다. 통째로 외워서 빈 화면에 바로 쓸 수 있어야 한다.

줄읽는 법
#include <stdio.h>printf와 scanf를 쓰겠다고 미리 알린다. 이 줄이 없으면 경고가 난다.
int main(void)정수를 돌려주고 인자를 받지 않는 시작 함수. void를 빼지 않는다.
int a, b;정수 변수 두 개를 만든다. 아직 값은 들어 있지 않다.
scanf("%d %d", &a, &b);공백으로 구분된 정수 두 개를 읽어 a와 b에 넣는다. &를 빠뜨리지 않는다.
printf("%d\n", a + b);합을 출력하고 줄을 바꾼다. 마지막 줄바꿈은 관례적으로 항상 넣는다.
return 0;정상 종료를 알린다.
INPUT
12 25
OUTPUT
37
왜 scanf에만 &가 붙는가 printf는 값을 가져다 쓰기만 하므로 값을 넘긴다. scanf는 변수에 값을 넣어야 하므로 그 변수가 있는 위치, 즉 주소를 넘긴다. &는 "이 변수의 주소"라는 뜻이다. 자세한 원리는 12장 포인터에서 다룬다. 지금은 "읽을 때는 &, 쓸 때는 안 붙임"으로 외워 둔다.

05 — 흔한 오류

흔한 오류 여섯 가지

아래 메시지는 모두 gcc 13.3.0에서 실제로 출력된 것을 그대로 옮긴 것이다. 메시지를 외울 필요는 없다. 어느 줄을 보라고 하는지, 그리고 그 줄이 진짜 범인인지를 판단하는 연습을 한다.

오류 1세미콜론 누락

6번 줄 scanf(...) 뒤의 세미콜론을 빠뜨렸다.

err1.c:6:27: error: expected ';' before 'printf'
    6 |     scanf("%d %d", &a, &b)
      |                           ^
      |                           ;
    7 |     printf("%d\n", a + b);

컴파일러는 printf를 만나고 나서야 "앞에 세미콜론이 있어야 했다"고 깨닫는다. 그래서 지목 위치가 6번 줄 끝이고, 친절하게 ;를 넣을 자리까지 표시해 준다.

고치는 법 — 지목된 위치보다 앞쪽을 본다. 오류 줄 번호의 바로 윗줄 끝을 먼저 의심한다.
오류 2헤더 파일 누락

#include <stdio.h>를 쓰지 않고 printf를 썼다.

err2.c:3:5: warning: implicit declaration of function 'printf'
            [-Wimplicit-function-declaration]
    3 |     printf("Hello, KOI!\n");
      |     ^~~~~~
err2.c:1:1: note: include '<stdio.h>' or provide a declaration of 'printf'

주목할 점은 이것이 error가 아니라 warning이라는 사실이다. 실행 파일은 만들어지고 프로그램은 Hello, KOI!를 정상 출력한다. 그래서 -Wall 없이 컴파일하면 이 실수를 전혀 눈치채지 못한다.

고치는 법 — 맨 위에 #include <stdio.h>를 추가한다. 그리고 경고를 무시하지 않는 습관을 들인다.
오류 3선언하지 않은 변수

int a;만 쓰고 b를 선언하지 않았다.

err3.c:6:25: error: 'b' undeclared (first use in this function)
    6 |     scanf("%d %d", &a, &b);
      |                         ^
err3.c:6:25: note: each undeclared identifier is reported only once
            for each function it appears in

이 메시지는 정직하다. 지목한 그 자리가 정확히 문제의 자리다. 두 번째 줄의 note는 "같은 이름은 한 번만 알려 준다"는 안내이므로, b를 쓴 다른 줄에서는 오류가 더 나오지 않는다는 뜻이다.

고치는 법 — 선언을 int a, b;로 고친다. 변수 이름 오타도 같은 메시지를 낸다.
오류 4중괄호 짝 불일치

마지막 닫는 중괄호 }를 빠뜨렸다.

err4.c:8:5: error: expected declaration or statement at end of input
    8 |     return 0;
      |     ^~~~~~

지목된 8번 줄 return 0;에는 아무 잘못이 없다. at end of input, 즉 파일이 끝나 버렸는데 블록이 안 닫혔다는 뜻이다. 중괄호 오류는 거의 항상 파일 맨 끝을 가리킨다.

고치는 법 — 파일 끝이 지목되면 줄 번호를 보지 말고 중괄호 짝부터 센다. 들여쓰기를 맞춰 두면 눈으로 바로 찾을 수 있다.
오류 5함수 이름 오타 — 링크 단계 오류

printf를 pritnf로 잘못 썼다.

err5.c:5:5: warning: implicit declaration of function 'pritnf';
            did you mean 'printf'? [-Wimplicit-function-declaration]
    5 |     pritnf("Hello, KOI!\n");
      |     ^~~~~~
      |     printf
/usr/bin/ld: err5.c:(.text.startup+0x12): undefined reference to `pritnf'
collect2: error: ld returned 1 exit status

메시지가 두 덩어리다. 앞쪽은 컴파일 단계의 경고이고, did you mean 'printf'?라고 고칠 이름까지 알려 준다. 뒤쪽 /usr/bin/ld:는 링크 단계에서 그런 함수를 찾을 수 없다는 오류다. 2.1절에서 본 네 단계 중 마지막 단계에서 막힌 것이다.

고치는 법 — undefined reference to가 보이면 함수 이름 철자나 파일 연결을 의심한다. 문법 오류가 아니므로 줄을 노려봐도 보이지 않는다.
오류 6scanf에서 & 누락 — 가장 위험한 실수

scanf("%d %d", a, b);처럼 &를 빠뜨렸다.

err6.c:6:13: warning: format '%d' expects argument of type 'int *',
            but argument 2 has type 'int' [-Wformat=]
    6 |     scanf("%d %d", a, b);
      |            ~^      ~
      |             |      |
      |             int *  int
err6.c:6:5: warning: 'a' is used uninitialized [-Wuninitialized]

컴파일러가 "int *를 기대했는데 int가 왔다"고 정확히 짚어 준다. 그런데 이것 역시 경고일 뿐이라 실행 파일은 만들어진다. 실행하면 다음과 같이 끝난다.

$ echo "3 4" | ./err6
Segmentation fault

엉뚱한 주소에 값을 쓰려다 운영체제에 의해 강제 종료된 것이다. 채점 결과로는 런타임 오류로 나온다.

고치는 법 — scanf를 쓸 때마다 변수 앞의 &를 눈으로 센다. -Wall을 켜 두면 실행 전에 반드시 걸린다.
이 장의 가장 중요한 교훈 오류 2·6에서 본 것처럼 경고가 있어도 프로그램은 만들어지고 실행된다. 그리고 그렇게 만들어진 프로그램은 조용히 틀린 답을 내거나 갑자기 죽는다. 경고 0개를 제출 기준으로 삼는다.
06 — 연습 문제

연습 문제 20문항

17

오류 메시지 예측 — 아래 코드를 gcc -std=c11 -Wall로 컴파일하면 어떤 메시지가 나올지 예측하고, 실제로 컴파일해 확인한 뒤 고쳐라. 컴파일 단계의 오류인지 링크 단계의 오류인지도 밝혀라.

#include <stdio.h>
int main(void)
{
    int a, b
    scnaf("%d %d", &a, &b);
    printf("%d\n", a + b)
    return 0;
}
18

같은 프로그램 찾기 — 아래 세 코드 중 컴파일러가 완전히 같다고 보는 것은 어느 것과 어느 것인가? 이유를 세미콜론과 블록의 규칙으로 설명하라.

(가) int main(void){int a;scanf("%d",&a);printf("%d\n",a);return 0;}

(나) int main(void)
     {
         int a; scanf("%d", &a);
         printf("%d\n", a); return 0;
     }

(다) int main(void)
     {
         int a;
         scanf("%d", &a)
         printf("%d\n", a);
         return 0;
     }

※ #include <stdio.h>는 세 코드 모두 맨 위에 있다고 가정한다.

19

종료 코드의 한계 — 두 정수를 입력받아 그 합을 printf 대신 return으로 돌려주는 프로그램을 작성했다. 입력이 100 200일 때 echo $?의 결과를 예측하고, 실제로 확인한 뒤 그 이유를 설명하라. 그리고 이 방식으로 답을 제출하면 안 되는 이유를 쓰라.

20

& 누락의 결과 분석 — scanf("%d", a);처럼 &를 빠뜨린 프로그램을 만들어 컴파일하라. ① 컴파일이 성공하는가 실패하는가 ② 경고 메시지는 무엇을 지적하는가 ③ 실행하면 어떻게 되는가 ④ 왜 컴파일러가 이것을 오류가 아닌 경고로 처리하는지, 세 질문에 답하라.

07 — 확인 평가 해설

정답과 해설

※ 이 절은 교사용 통합본에만 수록한다. 학생 배부용에서는 제거한다.

01
printf 세 번. 각 문자열 끝에 \n이 있는지 확인한다. 마지막 줄의 \n을 빠뜨리는 학생이 많다.
02
printf("*\n"); printf("**\n"); … 다섯 번. 지도 포인트 — 여기서 "반복문 있으면 좋겠다"는 불편을 학생이 직접 느끼게 둔다. 6장의 동기가 된다.
03
printf("He said \"C:\\temp\" twice.\n");
역슬래시 하나를 출력하려면 \\ 두 개를 쓴다. \t로 오인해 탭이 나오는 오답이 자주 나온다.
04
표준 코드와 동일. &와 세미콜론을 전부 확인한다.
05
printf("%d %d %d\n", a + b, a - b, a * b); — %d 개수와 값 개수가 모두 3인지 센다.
06
scanf("%d %d %d", &a, &b, &c); — 예제 2와 결과가 같음을 확인시킨다.
07
printf("%d %d\n", b, a); — 변수를 교환할 필요 없이 출력 순서만 바꾸면 된다는 점을 짚는다.
08
printf("%d\n%d\n", n * 2, n * 10); 또는 printf 두 번. 서식 문자열 안에 \n을 넣어 한 번에 처리할 수 있음을 보여 준다.
09
printf("%d %d\n", a / b, a % b); — 정수끼리의 /는 몫을 준다. 음수 나머지 문제는 4장에서 다룬다.
10
scanf("%lf %lf", &x, &y); printf("%.2f\n", (x + y) / 2); — 읽기 %lf, 쓰기 %f를 반드시 확인한다.
11
printf("%d\n%d\n", w * h, 2 * (w + h)); — 둘레 식의 괄호 누락이 흔한 오답이다.
12
printf("%d:%d\n", s / 60, s % 60); — 185 → 3:5. 지도 포인트 — 3:05로 출력하려면 %02d가 필요하다고 예고만 하고 3장으로 넘긴다.
13
int main(void){ return 42; }, 확인 명령은 ./a.out 실행 후 echo $?. 출력이 없으므로 화면에는 아무것도 나오지 않는 것이 정상이다.
14
fprintf(stderr, "sum:"); 후 printf("%d\n", a + b);. 2>/dev/null을 붙이면 합만 남는다. 채점기가 보는 것이 바로 이 상태임을 연결해 설명한다.
15
printf("%d\n", a / b);
printf("%.3f\n", (double)a / b);
(double) 형변환을 빠뜨리면 3.000이 나온다. 이 오답이 가장 많으며, 4장 형변환의 도입 사례로 쓴다.
16
scanf("%d,%d", &a, &b); — 서식 문자열에 쉼표를 그대로 쓰면 그 자리에 쉼표가 올 것을 기대한다. 확장 — 17, 25처럼 쉼표 뒤에 공백이 있어도 %d가 앞쪽 공백을 건너뛰므로 같은 코드로 동작한다.
17
실수는 세 군데다. 4번 줄 int a, b의 세미콜론 누락, 5번 줄 scnaf 오타, 6번 줄 printf(...)의 세미콜론 누락. 그런데 이 세 개가 한 번에 다 보이지 않는다는 것이 이 문제의 핵심이다.

1차 컴파일 — 세 개의 error가 나오지만 오타 scnaf는 지적되지 않는다. 
p17.c:5:5: error: expected '=', ',', ';', 'asm' or '__attribute__'
           before 'scnaf'
p17.c:6:24: error: 'b' undeclared (first use in this function)
p17.c:6:26: error: expected ';' before 'return'
4번 줄 선언이 문장으로 끝나지 못했으므로 컴파일러는 b가 선언된 적 없다고 본다. 즉 'b' undeclared는 가짜 오류이고, 진짜 원인은 4번 줄 하나다.

2차 컴파일(4번 줄 세미콜론만 고침) — 가짜 오류가 사라지고 오타가 드러난다. 
p17b.c:5:5: warning: implicit declaration of function 'scnaf';
            did you mean 'scanf'? [-Wimplicit-function-declaration]
p17b.c:6:26: error: expected ';' before 'return'
3차 컴파일(6번 줄도 고침) — 문법 오류가 모두 사라지자 비로소 링크 단계 오류가 나타난다. 
/usr/bin/ld: undefined reference to `scnaf'
collect2: error: ld returned 1 exit status
정리 — 세미콜론 누락은 컴파일 단계, scnaf 오타는 (경고를 무시하면) 링크 단계의 문제다. 링크 오류는 문법 오류가 전부 사라진 뒤에야 보이므로, 처음 메시지만 보고 "오류 세 개"라고 세면 안 된다.
지도 포인트 — 맨 위 오류 하나만 고치고 즉시 다시 컴파일한다는 원칙을 이 문제로 세운다. 아래쪽 오류를 먼저 붙잡는 학생이 가장 많이 헤맨다.
18
(가)와 (나)가 같다. 줄바꿈과 들여쓰기는 컴파일러에게 아무 의미가 없고, 문장의 끝은 세미콜론이 정하기 때문이다. (다)는 scanf(...) 뒤 세미콜론이 없어 컴파일 자체가 되지 않는다 — 오류 1과 같은 expected ';' before 'printf'가 나온다.
19
합은 300이지만 echo $?는 44를 출력한다. 종료 코드는 1바이트(0~255)만 전달되므로 300을 256으로 나눈 나머지가 남는다.
제출하면 안 되는 이유는 두 가지다. ① 256 이상의 값이나 음수를 표현할 수 없다 ② 채점기는 종료 코드가 0이 아니면 런타임 오류로 판정한다. 답은 언제나 stdout으로 출력한다.
20
① 컴파일은 성공한다(경고만 발생). ② format '%d' expects argument of type 'int *', but argument 2 has type 'int' — 주소를 기대했는데 값이 왔다고 지적한다. ③ 실행하면 대개 Segmentation fault로 죽고, 죽지 않더라도 변수에 예측할 수 없는 값이 남는다. ④ C 표준은 서식 문자열과 인자의 불일치를 정의되지 않은 동작으로 규정할 뿐 컴파일 오류로 못 박지 않는다. gcc가 서식 문자열을 들여다보고 내 주는 경고는 표준이 요구하는 것이 아니라 gcc의 호의다. 그래서 -Wall을 끄면 아무 말 없이 지나간다.
08 — 마무리

이 장을 마치기 전 점검

  • 빈 화면에서 add.c 표준 코드를 보지 않고 쓸 수 있다
  • gcc -std=c11 -Wall -o add add.c를 외워서 칠 수 있다
  • 컴파일 단계 오류와 링크 단계 오류를 메시지만 보고 구분할 수 있다
  • 오류 줄 번호가 진짜 범인이 아닐 수 있다는 것을 안다
  • 정답은 stdout, 디버깅 메시지는 stderr로 보낸다
  • 제출 전 경고가 0개인지 확인한다
다음 장 예고 — 02장 변수와 자료형, 오버플로 이 장에서는 int만 썼다. 그런데 1부터 100000까지의 합을 int로 계산하면 틀린 답이 나온다. 왜 그런지, 그리고 long long이 언제 필요한지를 다음 장에서 직접 확인한다.
