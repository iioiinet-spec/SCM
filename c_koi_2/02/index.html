02

제약 조건과 시간복잡도 감각

1장에서 "제약을 보고 자료형과 복잡도를 먼저 정한다"고 했다. 이 장은 그 판단의 근거를 만든다. 외워서 되는 일이 아니다. 직접 측정해서 몸에 붙이는 일이다. 이 장의 모든 숫자는 실제로 재서 적은 것이다.

학습 목표

  • 1초에 수행 가능한 연산 횟수를 측정해서 말할 수 있다
  • 루프 구조를 보고 복잡도를 O 표기로 셀 수 있다
  • N의 범위만 보고 허용되는 알고리즘을 고를 수 있다
  • 제약에서 최악의 값을 계산해 int와 long long을 결정할 수 있다
  • 같은 문제를 O(N²)와 O(N)으로 작성해 시간 차이를 직접 측정할 수 있다
  • 메모리 제한과 스택 한계를 구분하고 배열 선언 위치를 정할 수 있다

01 — 도입 문제

같은 답, 100배 다른 시간

문제
길이 N인 수열과 Q개의 질문이 주어진다.
각 질문은 두 수 L, R이며
A[L] + A[L+1] + ... + A[R] 을 출력한다.

제약
1 ≤ N, Q ≤ 100,000
1 ≤ A[i] ≤ 1,000,000,000
시간 제한 1초
가장 먼저 떠오르는 풀이
질문이 올 때마다
L부터 R까지 더해서 출력한다.

for (i = L; i <= R; i++)
    s += a[i];

맞는 답이 나온다.

맞는 답이 나온다는 것은 사실이다. 그런데 맞는 답이 제시간에 나오는가는 다른 질문이다. 두 가지 풀이를 모두 작성해 같은 입력으로 돌려 보았다.

무작위 L, R로 질문 10만 개
$ time ./naive  < big.txt
real    1.534s

$ time ./prefix < big.txt
real    0.051s
모든 질문이 L=1, R=N 일 때
$ time ./naive  < worst.txt
real    4.428s      ← 시간 초과

$ time ./prefix < worst.txt
real    0.041s
여기서 두 가지를 동시에 배운다 ① 같은 문제에 같은 답을 내는 두 코드의 시간이 100배 차이 난다.
② 무작위 입력으로는 1.5초, 최악의 입력으로는 4.4초다. 내가 만든 입력으로 돌려 보고 "빠르네"라고 판단하면 안 된다. 최악의 입력을 일부러 만들어야 한다.

느린 쪽의 연산 횟수를 세어 보자. 질문 하나마다 최대 N번 더하므로 Q × N = 105 × 105 = 1010번이다. 빠른 쪽은 미리 한 번 훑어 두고 질문마다 뺄셈 한 번이므로 N + Q = 2 × 105번이다. 5만 배 차이의 연산을 100배의 시간 차이로 막아 준 것은 컴파일러의 최적화이고, 그래도 4.4초는 4.4초다.

이 장이 답할 질문 ① 1초 동안 몇 번을 돌 수 있는가?
② 내 코드가 몇 번 도는지 어떻게 세는가?
③ N의 범위를 보고 어떤 방법이 허용되는지 어떻게 아는가?
02 — 개념 정리

개념 정리

2.11초는 얼마나 큰가

가장 단순한 반복문을 횟수를 늘려 가며 돌려 측정했다. 측정 환경은 Intel Xeon 2.10GHz, gcc 13.3.0이다.

반복 횟수-O2 (채점 기본)-O0 (최적화 없음)판정
106 (백만)0.001초0.001초눈 깜짝할 사이
107 (천만)0.004초0.013초여유
108 (1억)0.040초0.144초여유
109 (10억)0.508초1.318초아슬아슬
1010 (100억)약 5초약 13초시간 초과
왜 "1억 번에 1초"라고 가르치는가 위 표만 보면 10억 번도 0.5초다. 그런데 교재와 강의는 대부분 "1초에 1억 번"을 기준으로 말한다. 열 배나 보수적인 이유는 두 가지다.
① 위의 루프 몸통은 덧셈 하나뿐이다. 실제 문제의 몸통은 배열 접근·비교·나눗셈·함수 호출이 섞여 훨씬 무겁다.
② 채점 서버는 내 컴퓨터보다 느릴 수 있고, 다른 제출과 자원을 나눠 쓴다.
그래서 "1억 번이면 안전, 10억 번이면 위험"으로 기억한다. 측정값이 아니라 안전 기준이다.

2.2연산마다 비용이 다르다

같은 "1억 번"이라도 무엇을 1억 번 하는지에 따라 시간이 달라진다. 1억 회씩 측정한 결과다.

1억 회 수행한 작업시간비고
정수 덧셈만0.038초기준
배열 읽기 + 덧셈0.075초약 2배
배열 읽기 + 비교(if)0.070초약 2배
함수 호출0.120초약 3배
나머지 연산(%)0.148초약 4배

나눗셈과 나머지가 가장 비싸다. 루프 안쪽에서 %를 반복하고 있다면 그것만 빼도 눈에 띄게 빨라지는 경우가 있다. 다만 이 차이는 2~4배이고, 알고리즘을 바꾸면 100배다. 순서는 항상 알고리즘 먼저, 상수 나중이다.

2.3연산 횟수 세는 법

O 표기는 어려운 이론이 아니다. N이 커질 때 횟수가 몇 배로 늘어나는가를 적는 약속이다. 세는 규칙은 세 줄이면 끝난다.

코드 모양횟수표기
루프 하나NO(N)
루프 안에 루프N × NO(N²)
루프를 나란히 두 개N + N = 2NO(N) — 상수는 버린다
절반씩 줄어드는 반복log₂NO(log N)
정렬N log₂NO(N log N)
각 원소를 고르거나 말거나2NO(2N)
N개를 줄 세우는 모든 방법N!O(N!)
세어 보기 ①
for (i = 0; i < n; i++)
    for (j = 0; j < n; j++)
        s += a[i] * a[j];

→ n × n = O(N²)
세어 보기 ②
for (i = 0; i < n; i++)
    for (j = i+1; j < n; j++)
        if (a[i] < a[j]) c++;

→ n(n-1)/2 ≈ N²/2
→ 상수 1/2은 버리고 O(N²)
상수를 버리지만 무시하지는 않는다 위 ②는 ①의 절반이다. O 표기로는 둘 다 O(N²)이지만, 실제 시간은 두 배 차이다. O 표기는 "통과 가능성"을 판단하는 도구이고, 아슬아슬할 때는 상수까지 세야 한다.

2.4N을 보고 알고리즘을 고르는 표

이 표가 이 장의 핵심이다. 각 복잡도의 실제 실행 시간을 측정하고, 거기에 안전 여유를 둔 실전 기준을 함께 적었다.

제약의 N허용 복잡도대표 방법측정값 (1초 제한 기준)
N ≤ 10O(N!)모든 순열 시도N=10 → 0.083초 / N=11 → 1.08초 / N=12 → 12.9초
N ≤ 20O(2N)부분집합 전체 탐색N=24 → 0.026초 / N=26 → 0.122초 / N=28 → 0.378초
N ≤ 500O(N³)삼중 루프500³ = 1.25 × 108
N ≤ 5,000O(N²)이중 루프, 모든 쌍N=5,000 → 0.037초 / N=10,000 → 0.179초 / N=20,000 → 0.658초
N ≤ 500,000O(N log N)정렬 후 처리정렬 105 → 0.017초 / 106 → 0.181초
N ≤ 10,000,000O(N)한 번 훑기, 누적합107 → 0.016초 / 108 → 0.146초
N ≥ 109O(log N), O(1)수학 공식, 이분 탐색N을 다 훑는 것 자체가 불가능
측정값이 기준보다 넉넉한 이유 예를 들어 O(N²)의 측정값은 N=20,000에서도 0.658초다. 그런데 실전 기준은 N ≤ 5,000으로 잡았다. 루프 몸통이 비교 한 번이기 때문에 빠른 것이고, 실제 문제의 몸통은 더 무겁기 때문이다.
표를 외울 때는 왼쪽 두 칸만 외운다. 오른쪽은 "왜 그런지"의 근거다.
거꾸로 읽는 것이 진짜 사용법 문제에 N ≤ 1,000이라고 적혀 있으면 "O(N²)까지 허용한다"는 출제자의 신호다. N ≤ 100,000이면 "O(N²)로는 안 되니 다른 방법을 찾아라"는 신호다.
제약 조건은 힌트다. 문제를 받으면 N의 범위부터 보고 알고리즘의 후보를 좁힌다.

2.5제약에서 자료형을 결정한다

복잡도와 함께 반드시 계산하는 것이 결과의 최댓값이다. 1장의 체크리스트 5번이다.

도입 문제의 최악값 계산
A[i] ≤ 10^9 이고 N ≤ 10^5 이므로
구간 합의 최댓값은
  10^5 × 10^9 = 10^14

int 의 한계 = 2,147,483,647
            ≈ 2.1 × 10^9

10^14 > 2.1 × 10^9  →  long long
실제로 넘쳐 보면
int s = 0;
for (i = 0; i < 100000; i++)
    s += 1000000000;
printf("%d\n", s);
→ 276447232

long long t = 0;  (같은 반복)
→ 100000000000000

도입 문제의 실제 최대 구간 합을 측정했더니 50,027,818,288,216(약 5 × 1013)이었다. int였다면 전부 틀렸을 것이고, 컴파일러는 한마디도 하지 않는다.

자료형크기안전한 범위
int4바이트약 ±2.1 × 109 — 10자리부터 위험
long long8바이트약 ±9.2 × 1018 — 19자리까지
double8바이트정수는 약 9 × 1015까지만 정확(2장 참조)
판단 기준 한 줄 "답이 10자리를 넘을 수 있는가?" 조금이라도 넘을 가능성이 있으면 long long을 쓴다. 느려지지 않는다. 위 측정에서 long long 누적과 int 누적의 시간 차이는 없었다.

2.6메모리 제한과 스택

시간과 함께 적혀 있는 것이 메모리 제한이다. 보통 256MB다. int 하나가 4바이트이므로,

얼마나 들어가나
256MB / 4바이트 = 67,108,864개

int a[2000][2000]  → 15.3 MB   ○
int a[10000][10000] →  381 MB   ×
int a[10000000]    →  38.1 MB   ○
같은 배열, 선언 위치만 바꾸면
/* 전역 */
static int big[2000][2000];
→ 정상 동작

/* main 안의 지역 변수 */
int big[2000][2000];
→ Segmentation fault (종료 139)
메모리 제한과 스택 한계는 다른 것이다 메모리 제한 256MB를 넘지 않았는데도 터진다. 지역 변수는 스택에 잡히고 스택은 보통 8MB뿐이기 때문이다(ulimit -s로 확인하면 8192 KB).
규칙 — 큰 배열은 함수 밖(전역)에 선언한다. 덤으로 전역 배열은 0으로 자동 초기화된다.
03 — 표준 코드

표준 코드: 느린 판과 빠른 판

도입 문제의 두 풀이를 나란히 둔다. 입력·출력 부분은 완전히 같고 계산만 다르다는 점을 눈으로 확인한다.

naive.cO(N + Q·N) — 질문마다 다시 더한다
#include <stdio.h>

int a[100001];              /* 전역: 스택이 아니라 안전하다 */

int main(void) {
    int n, q;
    if (scanf("%d %d", &n, &q) != 2) return 1;
    for (int i = 1; i <= n; i++)
        if (scanf("%d", &a[i]) != 1) return 1;

    for (int k = 0; k < q; k++) {
        int l, r;
        if (scanf("%d %d", &l, &r) != 2) return 1;
        long long s = 0;      /* 질문마다 0으로 (1장 오류 2) */
        for (int i = l; i <= r; i++)
            s += a[i];           /* ← 여기가 최대 N번 */
        printf("%lld\n", s);
    }
    return 0;
}
prefix.cO(N + Q) — 미리 한 번만 더해 둔다
#include <stdio.h>

long long p[100001];        /* p[i] = A[1..i]의 합 */

int main(void) {
    int n, q;
    if (scanf("%d %d", &n, &q) != 2) return 1;
    for (int i = 1; i <= n; i++) {
        int x;
        if (scanf("%d", &x) != 1) return 1;
        p[i] = p[i - 1] + x;  /* 읽으면서 바로 누적 */
    }

    for (int k = 0; k < q; k++) {
        int l, r;
        if (scanf("%d %d", &l, &r) != 2) return 1;
        printf("%lld\n", p[r] - p[l - 1]);   /* 뺄셈 한 번 */
    }
    return 0;
}
p[l-1]을 위해 1번부터 쓴다 배열을 1번 칸부터 쓰면 l = 1일 때 p[0]을 읽게 되고, 전역 배열이므로 그 값은 0이다. 0번부터 썼다면 l == 0인지 매번 if로 검사해야 한다. 인덱스를 1부터 쓰는 습관이 경계 처리를 지운다.

3.1시간을 직접 재는 뼈대

터미널의 time 명령이 가장 간단하지만, 코드 안에서 특정 구간만 재고 싶을 때는 <time.h>의 clock()을 쓴다. 이 장의 모든 측정이 이 뼈대로 이루어졌다.

측정 뼈대이 장의 모든 표를 만든 코드
#include <stdio.h>
#include <time.h>

int main(void) {
    clock_t st = clock();           /* 시작 시각 */

    volatile long long s = 0;    /* volatile: 최적화로 지워지는 것을 막는다 */
    for (long long i = 0; i < 100000000; i++)
        s += i;

    double sec = (double)(clock() - st) / CLOCKS_PER_SEC;
    fprintf(stderr, "%.3f초\n", sec);   /* 측정값은 stderr로 (1장) */
    return 0;
}
volatile을 빼면 0.000초가 나온다 s를 쓰지 않으면 -O2 컴파일러는 루프 전체를 통째로 지운다. 결과가 아무 데도 쓰이지 않기 때문이다. 측정 코드를 쓸 때는 volatile을 붙이거나 마지막에 값을 출력해서 지워지지 않게 한다.

예제 1제약만 보고 알고리즘 말하기

코드를 쓰지 말고 표만 보고 판단한다. 이것이 이 장의 핵심 훈련이다.

제약허용 복잡도판단
N ≤ 1,000O(N²) 가능이중 루프로 모든 쌍을 봐도 된다
N ≤ 200,000O(N log N)까지이중 루프는 불가. 정렬이나 한 번 훑기
N ≤ 20O(2N) 가능부분집합을 모두 만들어도 된다 — 완전탐색 신호
N ≤ 8O(N!) 가능순서를 모두 바꿔 봐도 된다 — 순열 신호
N ≤ 1018O(log N) 이하반복문 자체가 불가능. 공식이나 이분 탐색

예제 2이중 루프를 한 줄로 줄이기

"수열에서 두 수를 골라 합이 K가 되는 쌍이 있는가?" N ≤ 100,000이라면 O(N²)는 1010이라 불가능하다.

O(N²) — 불가
for (i = 0; i < n; i++)
    for (j = i+1; j < n; j++)
        if (a[i] + a[j] == k) found = 1;

10^10회 → 시간 초과
O(N) — 체크 배열
/* 값이 0..1,000,000 범위라면 */
for (i = 0; i < n; i++) {
    int need = k - a[i];
    if (0 <= need && need <= 1000000
        && seen[need]) found = 1;
    seen[a[i]] = 1;
}
2 × 10^5회 → 통과

"이미 본 값"을 배열에 표시해 두면 안쪽 루프가 사라진다. 이 기법은 7장 배열 카운팅과 체크 배열에서 본격적으로 다룬다. 지금은 O(N²)를 O(N)으로 바꾸는 방법이 존재한다는 것만 확인한다.

예제 3복잡도 세기 연습

코드 ㉮
for (i = 0; i < n; i++)
    for (j = 0; j < m; j++)
        s += g[i][j];
코드 ㉯
for (i = 1; i <= n; i *= 2)
    for (j = 0; j < n; j++)
        s += j;

㉮는 O(N·M)이다. N²이 아니다. 두 변수가 다르면 곱해서 적는다. ㉯의 바깥 루프는 1, 2, 4, 8…로 커지므로 log₂N번 돌고, 안쪽이 N번이므로 O(N log N)이다. N = 105이면 log₂(105) ≈ 16.6이므로 약 166만 번이다.

예제 4최악의 입력을 직접 만든다

도입 문제에서 무작위 입력은 1.5초, 최악의 입력은 4.4초였다. 그 차이를 만든 것은 단 한 줄이다.

무작위 질문 (평균 길이 N/3)
for _ in range(q):
    l = random(1, n); r = random(1, n)
    if l > r: l, r = r, l
    print(l, r)
최악 질문 (항상 길이 N)
for _ in range(q):
    print(1, n)       ← 이 한 줄
최악 입력의 공식 ① 모든 값을 제약의 최댓값으로 (오버플로 확인)
② N과 Q를 제약의 최댓값으로 (시간 확인)
③ 루프가 가장 많이 도는 모양으로 (위의 1 n)
세 가지를 동시에 만족하는 입력을 만들어 돌려 본다. 그러고도 통과하면 제출한다.

예제 5입출력은 느리지 않다

"시간 초과가 났다 → 입출력이 느린가?"라는 의심을 자주 한다. 측정해 보면 그렇지 않다.

작업시간판정
scanf로 정수 100만 개 읽기0.050초문제없음
printf로 100만 줄 출력0.047초문제없음
printf마다 fflush 호출0.231초5배 느림 — 하지 말 것
결론 C의 scanf/printf는 브론즈 구간에서 병목이 아니다. 시간 초과가 났다면 알고리즘이 문제다. 단, 출력할 때마다 fflush(stdout)를 부르는 습관이 있다면 그것은 지운다. 디버깅이 끝났는데 남겨 둔 fflush가 흔한 범인이다.
05 — 흔한 오류

흔한 오류 여섯 가지

1
내 입력으로만 테스트하고 "빠르다"고 판단한다
도입 문제에서 무작위 입력 1.5초 / 최악 입력 4.4초였다. 직접 만든 작은 입력은 거의 항상 최악이 아니다.
대책 예제 4의 최악 입력 공식 세 가지를 적용한 파일을 만들어 time으로 잰다.
2
N이 작은 쪽만 보고 안심한다
"T ≤ 100이고 N ≤ 10,000이니까 둘 다 작네"가 아니다. T × N = 106이고, 각 케이스가 O(N²)면 100 × 108 = 1010이다.
대책 제약이 여러 개면 곱한 값을 계산한다. 1장 체크리스트 6번이 이것이다.
3
합을 int로 받는다
값이 109, 개수가 105면 합은 1014다. int는 2.1 × 109에서 끊긴다. 측정에서 276447232라는 그럴듯한 숫자가 나왔다.
대책 더하거나 곱하는 변수는 일단 long long으로 쓴다. 속도 손해는 측정상 없었다.
4
long long을 %d로 출력한다
변수는 제대로 선언했는데 서식이 %d면 하위 32비트만 찍히거나 쓰레기가 나온다. 컴파일 경고는 -Wall을 켜야 보인다.
대책 long long은 읽기 %lld, 쓰기 %lld로 짝을 맞춘다(3장).
5
큰 배열을 함수 안에 선언한다
int big[2000][2000];을 main 안에 두면 15.3MB가 스택에 올라가고, 스택은 8MB다. 결과는 컴파일 성공 후 Segmentation fault(종료 코드 139)다.
대책 큰 배열은 함수 바깥에 선언한다. 0 초기화도 따라온다.
6
상수 줄이기로 복잡도 문제를 해결하려 한다
1010번 도는 코드에서 %를 빼면 4배 빨라져 2.5 × 109번어치가 된다. 여전히 시간 초과다.
대책 순서는 복잡도 먼저, 상수 나중이다. O(N²)가 O(N)이 되면 100배지만, 상수 최적화는 최대 4배다.
이 장의 가장 중요한 교훈 오류 1·2·3은 모두 제출하기 전에 종이에서 잡을 수 있다. 제약을 읽고, 곱하고, 자릿수를 세는 것뿐이다. 코드를 다 쓰고 제출해서 "시간 초과"를 받고 나서야 복잡도를 세는 것이 가장 느린 길이다.

07 — 확인 평가

정답과 해설

01
⑴ O(N³) — 100³ = 106. O(N!)이나 O(2N)은 100에서는 불가능하다.
⑵ O(N²) — 2,000² = 4 × 106.
⑶ O(N log N) — 3 × 105 × 18 ≈ 5.4 × 106. O(N²)이면 9 × 1010으로 불가.
⑷ O(N) — 5 × 106. O(N log N)도 1.1 × 108로 가능하지만 아슬아슬하다.
⑸ O(log N) 또는 O(1) — 1012를 한 번 훑는 것조차 불가능하다. 공식이나 이분 탐색.
지도 포인트 — ⑷에서 "O(N)인가 O(N log N)인가"처럼 경계에 걸리는 경우가 실전에서 가장 많다. 이럴 때는 상수까지 본다.
02
㉮ O(N) — 루프 두 개를 나란히 둔 것이므로 N + N = 2N. 상수 2는 버린다.
㉯ O(N·M) — 변수가 다르면 곱해서 적는다. N²이 아니다.
㉰ O(log N) — i가 절반씩 줄어든다. N = 106이면 약 20번.
㉱ O(N³) — 정확히는 N(N-1)(N-2)/6 ≈ N³/6이지만 상수를 버린다.
지도 포인트 — ㉮와 ㉯를 헷갈리는 학생이 많다. 판별법은 "안에 있는가, 나란한가" 한 가지다. 중첩이면 곱하고, 나란하면 더한다.
03
⑴ 가능 — 104 × 104 = 108. int 한계 2.1 × 109보다 작다.
⑵ 불가, 1010 — int 한계의 약 5배. long long 필요.
⑶ 불가, 109 — 정확히는 106 × 103 = 109. 한계 2.1 × 109보다 작으므로 아슬아슬하게 가능하다. 그러나 여유가 2배뿐이라 long long을 권한다.
⑷ 불가, 약 5 × 109 — N(N+1)/2 = 105 × 105/2 = 5 × 109.
지도 포인트 — ⑶이 핵심이다. "가능하지만 여유가 없다"는 상태를 알아보는 것이 중요하다. 2배 여유면 제약이 조금만 달라져도 터진다. 2장에서 다룬 오버플로가 여기서 다시 나온다.
04
⑴ 가능 — 190.7MB (5 × 107 × 4바이트). 256MB 안이지만 여유가 적다.
⑵ 불가 — 305.2MB (4 × 107 × 8바이트).
⑶ 가능 — 95.4MB (5,000 × 5,000 × 4바이트 = 108바이트).
⑷ 불가 — 953.7MB (109개 × 1바이트).
지도 포인트 — 1MB = 1,048,576바이트다. 암산할 때는 "100만 바이트 ≈ 1MB"로 근사하고, 경계에 걸리면 정확히 계산한다. 그리고 ⑴·⑶처럼 통과하지만 여유가 없는 경우를 구분하게 한다.
05
① 첫 줄에 N = 100,000 (제약의 최댓값).
② 모든 값을 109 (제약의 최댓값) — 합이 1014가 되어 오버플로를 잡는다.
③ 질문이 있다면 모두 1 N (루프가 가장 많이 도는 모양).
지도 포인트 — 학생들은 "큰 입력"까지는 만들지만 ②와 ③을 빠뜨린다. 크기·값·모양 세 가지가 모두 최악이어야 한다. Python 세 줄이면 만들어지므로 손으로 만들지 않게 한다.
06
⑴ 부분집합 완전탐색 — N ≤ 20은 220 ≈ 106. "N ≤ 20"은 거의 언제나 2N 신호다.
⑵ 순열 완전탐색 — N ≤ 10은 10! ≈ 3.6 × 106. "방문 순서"는 순열의 전형적 표현이다.
⑶ 정렬 — 106은 O(N²) 불가, O(N log N) 가능. 측정값은 0.181초였다.
지도 포인트 — 이 문항이 이 장 전체의 목적이다. 제약은 힌트다. N ≤ 20을 보면 "완전탐색을 해도 된다는 허락"으로 읽는 훈련을 반복시킨다. 10장 완전탐색 입문에서 이 신호를 다시 쓴다.
07
⑴ 100 × 1,000² = 108 → 가능하나 아슬아슬.
⑵ 10 × (105 × 17) ≈ 1.7 × 107 → 여유롭게 가능.
⑶ 105 × 100² = 109 → 위험. 케이스마다 O(N²)를 O(N)으로 줄여야 한다.
지도 포인트 — ⑶이 오류 2의 전형이다. T도 100이고 N도 100이면 작아 보이지만, T가 105이면 이야기가 완전히 다르다. 항상 곱한다.
08
s의 값이 어디에도 쓰이지 않으므로 컴파일러는 루프 전체를 제거해도 프로그램의 동작이 같다고 판단한다. -O2는 이런 죽은 코드 제거를 수행한다.
다른 방법 — 루프가 끝난 뒤 printf("%lld\n", s);로 값을 실제로 출력한다. 쓰이는 값이 되면 지울 수 없다.
지도 포인트 — 이것은 1장에서 다룬 "-O2가 코드를 바꾼다"의 연장이다. 측정 코드를 쓸 때는 내가 재려는 것이 실제로 실행되는지부터 확인한다. 0.000초가 나오면 거의 항상 지워진 것이다.
09
본문 3.1절 뼈대 그대로. 측정 결과는 -O0이 -O2보다 3~4배 느리다(본문 2.1절 표: 1억 회에서 0.144초 대 0.040초).
지도 포인트 — 채점 서버는 보통 -O2로 컴파일한다. 내 컴퓨터에서 -O0으로 재고 "느리다"고 판단하면 과하게 비관하게 된다. 측정은 -O2로 한다.
10
본문 prefix.c와 동일. 채점 포인트 네 가지 —
① p를 long long으로 선언했는가 (1014)
② 배열을 1번부터 썼는가 (p[l-1]의 경계)
③ p를 전역에 두었는가
④ 출력 서식이 %lld인가
지도 포인트 — 누적합은 "읽으면서 바로 더한다"가 핵심이다. 원본 배열을 따로 저장할 필요가 없다. 메모리와 코드가 동시에 줄어든다.
11
측정값 — 느린 판 4.428초, 누적합 판 0.041초. 약 108배.
무작위 질문일 때는 1.534초 대 0.051초로 약 30배였다. 최악 입력일수록 차이가 커진다.
지도 포인트 — 숫자를 직접 보게 하는 것이 이 문항의 전부다. "O(N²)는 느리다"는 말보다 4.428 / 0.041이라는 두 숫자가 오래 남는다. 측정 결과를 공책에 표로 적게 한다.
12
첫 N = 65,536. 검산 — N(N+1)/2 가 231 = 2,147,483,648을 처음 넘는 지점이다. N = 65,535면 2,147,450,880으로 INT_MAX(2,147,483,647) 이하이고, N = 65,536이면 2,147,516,416으로 넘는다.
지도 포인트 — 2장에서 한 실험과 같은 문제다. 여기서는 제약을 보고 미리 예측한 뒤 실험으로 확인하는 순서를 지키게 한다. 예측 없이 돌리면 실험이 아니라 구경이다.
13
측정값 — N=1,000 → 0.001초 / 5,000 → 0.037초 / 10,000 → 0.179초 / 20,000 → 0.658초.
N이 2배가 될 때 시간은 약 4배가 된다(0.179 → 0.658은 3.7배). O(N²)의 정의 그대로다.
지도 포인트 — "N이 2배면 시간은 4배"를 측정으로 확인하는 것이 목적이다. 같은 방법으로 O(N)이면 2배, O(N³)이면 8배가 된다. 이 비율을 보면 내 코드의 복잡도를 역으로 알아낼 수 있다.
14
각 원소에 대해 "넣는다 / 안 넣는다" 두 갈래로 재귀하면 잎이 2N개다.
측정값 — N=20 → 0.002초 / N=24 → 0.026초 / N=26 → 0.122초 / N=28 → 0.378초.
N이 1 늘 때마다 시간이 2배가 된다.
지도 포인트 — 지수 복잡도의 무서움은 "N을 1만 늘려도 2배"라는 데 있다. N ≤ 20이 안전 기준인 이유, 그리고 N = 40이면 1012라서 손도 못 대는 이유를 여기서 체감시킨다.
15
측정값 — N=8 → 0.001초(40,320가지) / N=10 → 0.083초(3,628,800) / N=11 → 1.083초(39,916,800) / N=12 → 12.910초(479,001,600).
예측 — N=11이 1.083초였으므로 N=12는 12배인 약 13초. 실측 12.910초로 거의 정확하다.
지도 포인트 — N!은 N이 1 늘 때 N배가 된다. 2N이 2배씩 느는 것과 비교하면 훨씬 가파르다. 참고로 N=13은 약 168초, N=14는 약 40분이다. "N ≤ 10이면 순열"이라는 기준이 왜 그렇게 작은지가 설명된다.
16
⑴ Segmentation fault, 종료 코드 139 — 15.3MB를 8MB 스택에 올리려 했다.
⑵ 정상 동작, 종료 코드 0.
두 코드의 차이는 int big[2000][2000]; 줄의 위치 하나다.
지도 포인트 — 139 = 128 + 11이고 11은 SIGSEGV다. 종료 코드를 보면 "틀렸습니다"가 아니라 "런타임 에러"의 원인을 짐작할 수 있다. ulimit -s로 스택 크기를 직접 확인하게 한다(보통 8192 KB).
17
본문 2.2절 — 덧셈 0.038 / 배열 읽기 0.075 / 나머지 0.148 / 함수 호출 0.120초.
값이 다른 이유 — ① CPU 모델과 클럭이 다르다 ② 컴파일러 버전과 최적화 옵션이 다르다 ③ 다른 프로그램이 같이 돌고 있다 ④ 캐시에 올라와 있는지에 따라 배열 접근 속도가 달라진다.
지도 포인트 — 절대값이 아니라 비율을 보게 한다. 어느 컴퓨터에서 재도 "나머지 연산이 덧셈보다 3~4배 비싸다"는 관계는 유지된다. 그리고 이 차이가 알고리즘 차이(100배)보다 작다는 것을 다시 짚는다.
18
복잡도 — 단순 방법은 질문마다 최대 N² = 106칸을 훑으므로 Q × N² = 105 × 106 = 1011. 불가능하다.
2차원 누적합 — P[i][j] = g[i][j] + P[i-1][j] + P[i][j-1] - P[i-1][j-1]로 만든 뒤,
질문은 P[r2][c2] - P[r1-1][c2] - P[r2][c1-1] + P[r1-1][c1-1] 한 줄이다. 전체 O(N² + Q) = 1.1 × 106.
메모리 — long long P[1001][1001]은 약 8MB이므로 반드시 전역에 둔다.
지도 포인트 — 겹치는 부분을 두 번 빼고 한 번 더하는 포함-배제가 핵심이다. 3 × 3 격자에 직접 그려 가며 네 항을 손으로 확인시킨다. 9장 2차원 격자에서 이 식을 다시 쓴다.
19
⑴ (106)² = 1012 — 1초에 108~109이므로 1,000초 이상이다. 확실히 떨어진다.
⑵ 3,000² = 9 × 106으로 O(N²)도 통과한다. 출제 의도가 무너진다.
⑶ O(N log N)은 106 × 20 = 2 × 107로 여유롭게 통과하고 O(N²)는 확실히 탈락하는 지점이기 때문이다. 두 조건을 동시에 만족하는 N을 고른 것이다.
지도 포인트 — 출제자의 입장에서 제약을 보게 하는 문항이다. 이 관점이 생기면 제약을 읽는 순간 의도가 보인다. 12장 브론즈 실전 모의에서 이 시각을 다시 쓴다.
20
체크리스트(1장)
1. 입력 유형 — ② N개 (첫 줄에 N, K / 다음 줄에 N개)
2. 한 케이스 — N, K와 N개의 정수. 케이스는 하나
3. 출력 — 한 줄, 정수 하나
4. 범위 — N ≤ 106, 값 ≤ 109, K ≤ N
5. 최악의 값 — K개의 합이 최대 106 × 109 = 1015 → long long
6. 복잡도 — N ≤ 106이므로 O(N) 또는 O(N log N). 모든 시작점마다 K개를 더하면 N × K = 1012로 불가
7. 경계 입력 — K = 1 / K = N / N = 1 / 모든 값이 109이고 N = K = 106

메모리 — int a[1000001]은 4MB. 누적합을 쓰면 long long p[1000001]로 8MB. 둘 다 256MB 안이지만 전역에 선언한다(8MB는 스택 한계와 같아 위험하다).
코드 — 누적합으로 p[i] - p[i-K]를 i = K..N에서 최대로 취하거나, 슬라이딩 윈도로 s += a[i] - a[i-K]를 굴린다. 둘 다 O(N)이다.
지도 포인트 — 6번이 핵심이다. "연속한 K개"라는 말에 이끌려 이중 루프를 쓰면 1012다. 제약을 먼저 보면 이중 루프를 아예 시도하지 않는다. 그리고 5번에서 1015를 계산해 두지 않으면 int로 쓰고 틀린다. 이 장의 모든 내용이 한 문제에 들어 있다.
08 — 마무리

이 장을 마치기 전 점검

  • "1초에 1억 번"을 안전 기준으로 기억한다 (측정값은 더 넉넉하다)
  • 루프가 중첩이면 곱하고 나란하면 더한다
  • 제약이 여러 개면 곱한 값을 계산한다 (T × N)
  • N의 범위를 보고 허용 복잡도를 말할 수 있다 (10 / 20 / 500 / 5,000 / 500,000 / 107)
  • 답의 최댓값이 10자리를 넘으면 long long을 쓴다
  • 큰 배열은 함수 바깥에 선언한다 (스택은 8MB)
  • 최악의 입력을 직접 만들어 time으로 잰다
  • 시간 초과는 입출력이 아니라 알고리즘의 문제다
다음 장 예고 — 03장 조건 분기형 문제 1장에서 문제를 읽는 절차를, 2장에서 방법을 고르는 기준을 만들었다. 3장부터는 실제 문제 유형으로 들어간다. 첫 유형은 조건 분기다. 등급 판정, 윤년, 삼각형 종류처럼 경우를 빠짐없이 나누는 문제에서, 조건의 순서를 어떻게 잡아야 중복과 누락이 사라지는지를 다룬다.
